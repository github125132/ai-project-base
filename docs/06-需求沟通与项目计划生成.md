# 需求沟通与项目计划生成(三阶段工作流之二)

> 前置:已完成 [`00-项目初始化引导.md`](./00-项目初始化引导.md)。
> 后置:进入 [`07-子任务并行执行与Git自动化.md`](./07-子任务并行执行与Git自动化.md)。

本阶段的目标:**把用户口头的"项目描述"沉淀为可执行、可并行、可追溯的开发计划与子任务文档**,并把这套文档一次性提交推送到根仓主分支。

## 1. 判定是否需要本阶段

满足下列任一条件:

- `docs/01-项目要求.md` 中的"业务模块"小节仍是 `TODO(新项目维护者填写)`
- `docs/05-项目开发进度总览.md` 的"业务模块进度"或"排期"表内容为占位
- `docs/progress/` 下没有任何 `{N}-{topic}.md` 子任务文档(模板与 README 不计)

满足时,**先完成本阶段**才能进入子任务执行。

## 2. 沟通输入(必须从用户处确认)

| 项 | 用途 | 必需 |
|----|------|------|
| 项目一句话描述 | 写入 `01` 项目定位 | 是 |
| 目标用户与场景 | 多端范围、UI 风格 | 是 |
| 业务模块清单(3–10 个) | `01` 业务模块、`05` 模块进度 | 是 |
| 每个模块的核心实体与关键字段 | 子任务文档数据模型 | 是 |
| 状态/类型字典清单 | 字段双轨规则归类 | 是 |
| 必须的端 | PC / APP / 大屏 / H5 | 是 |
| 截止日期或硬约束 | Sprint 排期 | 否 |
| 已知风险 | `05` 风险表 | 否 |

如果用户描述有歧义或字段不全,**用 AskUserQuestion 一次性收齐**,不要反复打断用户。

## 3. 生成产物清单(原子提交)

本阶段一次性产出以下文档,作为**一个 Git 提交**进入根仓主分支:

1. `docs/01-项目要求.md` 的"业务模块"、"多端范围"、"UI 原则"三处 TODO 全部填写
2. `docs/05-项目开发进度总览.md` 的"业务模块进度"与"排期与优先级"两张表
3. `docs/progress/{N}-{module}-{topic}.md` 多个子任务文档(详见下节)
4. `docs/progress/README.md` 文末追加依赖关系图(mermaid 或纯文本)

## 4. 子任务文档生成规则

### 4.1 拆分粒度

- 每个子任务 = **一个可独立验收的特性**(典型规模:1 个核心实体的 CRUD + 关联接口 + 列表表单页 + 字典 + 权限)
- 子任务跨越的子仓不超过 2–3 个(后端、管理端、(可选)移动端)
- 单子任务的预估改动 < 800 行,超过则继续拆

### 4.2 命名与编号

```text
docs/progress/{优先级}-{序号}-{模块}-{主题}.md

示例(默认 gap 项目):
docs/progress/p0-01-base-基地管理.md
docs/progress/p0-02-plot-地块管理.md
docs/progress/p0-03-dict-基础字典.md
docs/progress/p1-04-doc-文件管理.md
```

- 前缀 `p0/p1/p2/p3` 表示优先级
- 序号在同优先级内连续
- `{模块}` 小写,对应 `{{PERM_PREFIX}}:{模块}:*`
- `{主题}` 中文,可读

### 4.3 必填字段(基于 `progress/TEMPLATE-功能设计与开发记录.md`)

- 基本信息 + **依赖关系** + **可并行标志**
- 需求背景、本次范围、不在本次范围
- 数据模型、字典与状态(声明走字典分支 or `statusName` 分支)
- 接口设计(路径前缀 `{{API_PREFIX_ADMIN}}` / `{{API_PREFIX_APP}}`)
- 页面与交互
- 权限与菜单(权限码 `{{PERM_PREFIX}}:{模块}:{动作}`)
- 附件、导出、留痕策略
- 验收标准(checkbox 列表)
- **Git 分支名**:`feature/{progress-file-stem}`,例如 `feature/p0-01-base-基地管理`

### 4.4 依赖与并行

每篇子任务文档"基本信息"区追加两行:

```markdown
| 依赖 | 例如：p0-03-dict-基础字典(字典先行) |
| 可并行 | 是/否(取决于依赖是否就绪) |
```

依赖关系也可以在 `docs/progress/README.md` 的索引区用 mermaid 一图概览。

## 5. 计划生成的提交动作

完成以上产物后,AI 自动执行:

```bash
cd <PROJECT_ROOT>
git status -sb                                     # 预检
git add docs/ AGENTS.md
git commit -m "文档: 生成项目计划与子任务设计({{PROJECT_CODE}})"
git push origin main                               # 主分支名按实际仓库
```

- 提交前用 `grep -R "TODO(新项目维护者填写)" docs/` 确认无遗留占位
- 推送前 `git status` 确认无 `.env`、`project.config.yaml` 误入暂存
- push 失败时(冲突、权限)**不重试**,直接报告给用户

## 6. 与用户确认的节点

本阶段需在以下三处停下,征求用户确认后再继续:

1. **业务模块清单确认**:列出 AI 从用户描述中识别出的模块,等待用户增删
2. **子任务拆分草案确认**:展示 `docs/progress/` 下计划生成的文件列表与依赖图,等待用户调整
3. **提交推送前确认**:展示 `git diff --stat`,等待用户放行 push

不要在用户未确认时直接 push 到 main。

## 7. 禁止事项

- 不要修改"不可变基础"(见根 AGENTS.md "不可变基础 vs 项目专属内容")
- 不要把 `docs/examples/` 当真业务参考写入子任务,examples 只读
- 不要在本阶段动子仓代码,本阶段只产出文档
- 不要把多个子任务塞进同一篇文档
- 不要把状态字段双轨规则混用,每个字段在子任务文档里明确归属哪一类
