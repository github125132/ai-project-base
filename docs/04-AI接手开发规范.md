# AI 接手开发规范

## 1. 接手目标

AI 接手本项目后,应先理解项目结构、仓库边界、业务目标和开发规范,再进行具体功能开发。

最小判断:

```text
这是 中药材GAP基地全流程服务平台。
根仓负责项目文档,后端、管理端、移动端分别是独立代码仓。
后端基于 ruoyi-vue-pro,管理端基于 yudao-ui-admin-vue3,移动端基于 uniapp。
开发时必须保持现有框架风格,不重建工程。
```

> 若仓库内仍有 `{{...}}` 占位符或 `project.config.yaml` 缺失,先按 [`00-项目初始化引导.md`](./00-项目初始化引导.md) 完成初始化,再进入业务开发。

## 2. 必读顺序

唯一权威必读清单维护在 [`docs/README.md`](./README.md)。本文不重复列出,避免清单漂移。

## 3. 工作流

```text
理解需求 -> 判断涉及仓库 -> 查进度总览和相关子文档 -> 查现有代码风格 -> 设计实现方案 -> 更新或创建开发记录 -> 修改代码 -> 验证 -> 更新进度文档 -> 分仓提交推送
```

### 开发前自检清单

每项功能开始编码前，逐项确认：

```text
[ ] 已读根仓 AGENTS.md 和 docs/01-项目要求.md，知道项目是什么
[ ] 已读 docs/05-项目开发进度总览.md，清楚当前阶段和已有模块
[ ] 已读 docs/progress/ 下本次相关子文档（如有），了解前人设计决策
[ ] 已读对应子仓 AGENTS.md（后端/管理端/移动端），掌握分层和命名规范
[ ] 明确了本次任务属于哪个业务模块
[ ] 明确了涉及哪些仓库和端（后端/管理端/移动端/大屏/H5）
[ ] 明确了是否需要新增数据库表、菜单、权限、字典、枚举
[ ] 明确了是否需要状态流转、审计留痕、导出、附件、定位、扫码
[ ] 明确了所有用户可见文案是否全部使用中文
[ ] 明确了状态字段走哪个分支（字典 → dict-tag / 枚举 → statusName）
[ ] 已确认依赖的子任务是否已完成（跨子任务时）
[ ] 已有或已创建 docs/progress/ 子文档
```

此清单不需要逐条回复，心中有数即可。每项不确定时停下来查。

## 3.1 文档进度维护规范

项目开发必须维护两层进度记录:

- 总览文档:`docs/05-项目开发进度总览.md`
- 子文档:`docs/progress/` 下的功能设计与开发记录

要求:

- 新功能开发前,先查看总览文档和相关子文档,确认当前状态、遗留事项和风险
- 如果没有对应子文档,复制 `docs/progress/TEMPLATE-功能设计与开发记录.md` 建立一篇新文档
- 子文档必须记录需求范围、涉及仓库、涉及端、数据模型、接口、页面、权限、字典、状态、验证和提交信息
- 一项功能完成后,必须更新总览文档中的模块状态、最近变更和风险事项
- 总览文档不写过细实现,详细设计和开发过程写入子文档
- 不保留零散临时流水账,所有记录都要能服务后续接手、验证和追溯

## 4. 后端开发规范

后端继续遵循 ruoyi-vue-pro 当前代码结构。

业务模块优先放入:

```text
ai-project-server/yudao-module-gap/
```

推荐包结构:

```text
cn.iocoder.yudao.module.gap
├── controller/admin/{domain}/vo/
├── controller/app/{domain}/vo/
├── service/{domain}/
├── dal/dataobject/{domain}/
├── dal/mysql/{domain}/
├── convert/{domain}/
├── enums/
├── api/
└── framework/
```

要求:

- Controller 只做参数接收、权限控制、Swagger 说明、调用 Service 和返回结果
- Service 负责业务校验、事务、状态流转、审计留痕和跨 Mapper 协调
- Mapper 继承 `BaseMapperX`,查询使用 `LambdaQueryWrapperX`
- DO 继承 `BaseDO`
- VO 使用 `@Schema` 和 jakarta validation,校验提示中文
- 错误码集中维护在 `ErrorCodeConstants.java`
- 管理端接口权限使用 `@PreAuthorize`
- 权限码使用 `gap:{资源}:{动作}`
- 常规 CRUD 路径使用 `/create`、`/update`、`/delete`、`/delete-list`、`/get`、`/page`、`/export-excel`

## 5. 管理端开发规范

管理端继续遵循 yudao-ui-admin-vue3 当前代码结构。

接口路径:

```text
ai-project-admin-web/src/api/gap/{resource}/index.ts
```

页面路径:

```text
ai-project-admin-web/src/views/gap/{resource}/index.vue
ai-project-admin-web/src/views/gap/{resource}/{Resource}Form.vue
```

要求:

- 请求使用 `@/config/axios`
- 列表页沿用 `ContentWrap`、`Pagination`、`Icon`、`dict-tag`
- 表单弹窗沿用 `Dialog`
- 常用变量命名:`loading`、`total`、`list`、`queryParams`、`queryFormRef`、`formRef`
- 常用方法命名:`getList`、`handleQuery`、`resetQuery`、`openForm`、`handleDelete`、`handleExport`
- 权限按钮使用 `v-hasPermi`
- 代码格式:2 空格缩进、单引号、不使用分号

## 6. 移动端开发规范

移动端继续遵循 uniapp + Vue 3 + TypeScript + Pinia + Wot Design Uni。

要求:

- 页面、按钮、表单、提示、空状态、错误信息、状态标签使用中文
- 接口对接 `/app-api/gap/{功能}`
- 现场操作优先考虑拍照、定位、扫码、时间留痕
- 状态、类型、关键结论展示中文
- 不直接展示后端状态码、枚举名、英文编码

## 7. 展示文案与状态要求

所有端统一遵守:

- 用户可见信息必须中文
- 不展示 `DRAFT`、`APPROVED`、`status=1`、`true/false` 等用户不可理解内容
- 后端固定业务状态使用枚举;禁止魔法数或裸字符串判断、更新状态
- 状态更新必须经过 Service 层业务方法
- 审核、归档、整改、关键结论等状态必须留痕

### 状态字段双轨规则(与根 AGENTS.md 一致)

| 场景 | 后端返回 | 前端展示 |
|------|----------|----------|
| 字段存在系统字典(`dict_type` 已注册) | 仅返回 `status`(字典值) | `<dict-tag :type="..." :value="status" />` |
| 字段是枚举或规则计算结果(无字典) | 同时返回 `status` + `statusName` | 直接渲染 `statusName` |

同一字段二选一,不混用。新增字段时必须在 `docs/progress/` 子文档中声明属于哪一类。

## 8. 禁止事项

- 不要把现有项目当成空项目重新初始化
- 不要修改 `yudao-framework` 核心代码,除非明确是框架级问题
- 不要把业务堆到 `system` 或 `infra`,必须放入 `yudao-module-gap`
- 不要绕过现有请求封装和 UI 组件体系
- 不要提交 `node_modules`、`dist`、`unpackage`、日志文件
- 不要回滚用户已有改动
- 不要把子仓源码提交到根仓
- 不要只做表单录入,业务重点是证据、状态、审计、闭环
